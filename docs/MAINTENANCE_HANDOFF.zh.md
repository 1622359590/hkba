# HKBA 网站与 CMS 维护交接手册

> 适用对象：一名主开发者配合 AI 编程助手  
> 项目仓库：`https://github.com/1622359590/hkba.git`  
> 默认分支：`main`  
> 最后整理：2026-09-07

## 1. 交接目标

维护工作的首要目标不是继续堆功能，而是让网站和后台更稳定、更容易理解、更容易使用。

接手者需要负责三类工作：

1. 后端稳定性：数据库、权限、接口、备份、迁移和部署可靠。
2. 后台易用性：管理员能快速找到工作、理解状态并安全完成编辑和发布。
3. 日常交付：所有改动通过分支、测试、Pull Request 和 GitHub Actions 上线。

建议由一名开发者拥有最终判断权，AI 负责代码检索、测试先行、实现、审查清单和文档更新。AI 不应直接决定产品规则、删除生产数据、修改密钥或绕过发布检查。

## 2. 当前系统概览

### 2.1 技术架构

| 部分 | 技术 | 主要目录 | 默认端口 |
| --- | --- | --- | --- |
| 前端 | Next.js 16、React 19、TypeScript | `frontend/` | `5001` |
| 后端 | Express、Node.js | `backend/` | `5002` |
| 数据库 | SQLite、顺序迁移脚本 | `backend/db/` | — |
| 媒体 | 本地上传或阿里云 OSS | `backend/uploads/`、后台存储设置 | — |
| 部署 | GitHub Actions、rsync、PM2、宝塔 Nginx | `.github/workflows/deploy-baota.yml` | — |

浏览器只访问前端。Next.js 将 `/api/*` 和 `/uploads/*` 转发到内部后端，生产环境不应直接公开 `5002` 端口。

### 2.2 主要功能区域

- 公开网站：首页、关于协会、新闻、活动、会员单位、团队、加入协会、联络页面。
- 管理后台：仪表盘、页面树、组件工作室、新闻、活动、Banner、团队、会员、媒体、留言和设置。
- 内容发布：草稿、版本、预览、发布检查、撤回、历史回退。
- 管理能力：角色权限、审计日志、媒体引用保护、数据库迁移与部署备份。

### 2.3 关键代码入口

| 目的 | 位置 |
| --- | --- |
| 后端服务入口 | `backend/server.js` |

## 3. 项目负责人需要先做的事

### 3.1 推荐的交接方式：GitHub 协作者

不要每天通过压缩包来回覆盖代码。推荐让维护人员使用自己的 GitHub 账号：

1. 打开 GitHub 仓库。
2. 进入 `Settings` → `Collaborators and teams`。
3. 添加维护人员的 GitHub 用户名。
4. 普通维护只授予 `Write` 权限，不授予仓库管理员权限。
5. GitHub Actions 密钥只由项目负责人管理，不通过微信、邮件或文档发送。

建议为 `main` 开启分支保护：必须通过 Pull Request 合并、禁止强制推送、合并前必须通过测试。维护人员日常只推送功能分支。

### 3.2 负责人需要单独保管的资料

以下资料不要写入 Git、AI 提示词或本手册：

- 服务器 SSH 私钥和登录密码；
- GitHub Actions Secrets；
- 生产 `JWT_SECRET`；
- 管理后台密码；
- 阿里云 OSS Access Key；
- 生产数据库和真实用户资料。

如果维护者确实需要操作生产环境，应通过密码管理器或临时授权单独交接，并在工作结束后回收权限。

## 4. 如何下载代码

### 4.1 首次下载：推荐使用 Git

先安装 Node.js 20 或更新版本、Git，然后运行：

```bash
git clone https://github.com/1622359590/hkba.git
cd hkba
git switch main
git pull --ff-only
```

如果仓库是私有的，执行前先登录 GitHub CLI：

```bash
gh auth login
gh auth status
```

### 4.2 只想查看代码：下载 ZIP

在 GitHub 仓库点击 `Code` → `Download ZIP`。这种方式适合阅读和备份，不适合长期开发，因为 ZIP 没有提交历史，也不方便安全上传修改。

### 4.3 每次开始工作前更新代码

```bash
cd hkba
git switch main
git pull --ff-only
git switch -c feat/简短任务名称
```

分支名示例：

- `feat/admin-form-feedback`
- `fix/news-publish-error`
- `refactor/backend-response-envelope`

不要直接在 `main` 上开发。

## 5. 本地安装与启动

### 5.1 后端

```bash
cd backend
npm install
cp .env.example .env
npm run dev
```

本地 `.env` 至少设置：

```dotenv
PORT=5002
JWT_SECRET=仅用于本地且至少32个字符的随机字符串
ADMIN_INITIAL_PASSWORD=仅用于本地且至少12个字符的密码
ALLOWED_ORIGINS=http://localhost:5001,http://127.0.0.1:5001
```

不要把 `backend/.env` 提交到 Git。

后端健康检查：

```bash
curl --fail http://127.0.0.1:5002/api/health
```

### 5.2 前端

另开一个终端：

```bash
cd frontend
npm install
npm run dev
```

访问：

- 网站：`http://localhost:5001`
- 后台：`http://localhost:5001/admin/login`

本地默认由 Next.js 把 API 请求转发到 `127.0.0.1:5002`，通常不需要前端环境文件。

## 6. 一个人配合 AI 的工作规范

### 6.1 人负责什么

- 明确用户问题、业务规则和优先级；
- 决定数据库结构、权限规则和界面流程；
- 审查 AI 生成的差异和测试；
- 决定是否合并、部署或回滚；
- 保管生产权限和密钥。

### 6.2 AI 负责什么

- 阅读相关代码和现有设计文档；
- 先编写失败测试，再实现功能；
- 只修改当前任务范围内的文件；
- 运行完整测试和生产构建；
- 总结改动、风险和手工验证步骤；
- 更新使用说明和迁移说明。

### 6.3 每次任务必须遵守的顺序

1. 写清用户问题和成功标准。
2. 让 AI 先定位代码与影响范围，不立即修改。
3. 确认方案后建立功能分支。
4. 先增加回归测试，再实施修改。
5. 检查 `git diff`，确认没有密钥、数据库和无关文件。
6. 运行第 10 节的全部验证。
7. 推送分支并创建 Pull Request。
8. 人工检查关键界面和数据行为。
9. 合并 `main`，观察自动部署和冒烟检查。
10. 将结果和遗留问题写回 PR。

## 7. 维护需求清单

下面的任务按优先级安排。一个人维护时，应一次只做一个任务，每个任务单独建立分支和 PR。

### P0：先保证系统可靠

#### P0-1 统一后端接口和权限边界

现状：仓库同时保留传统 `/api/...` 路由和新版 `/api/admin/...` 内容接口，部分传统写接口只检查登录，没有使用细粒度权限。

要求：

- 盘点所有写接口，明确 `content.read`、`content.write`、`publish`、`rollback`、`media.delete`、`system.admin` 的适用范围；
- 传统 Banner、团队、活动、会员、留言等写接口补齐一致的权限检查；
- 新代码统一使用 `{ data, error }` 响应结构和稳定错误码；
- 不在一次改动中删除旧接口，先完成调用迁移和兼容测试。

验收：未登录返回 401、无权限返回 403、校验失败返回可显示到字段的错误信息；现有公开接口行为不变。

#### P0-2 生产备份与恢复演练

要求：

- 确认每日定时运行 `backend/scripts/backup-db.js`；
- 备份文件保存至少 30 天，并监控备份失败；
- 在非生产目录完成一次真实恢复演练；
- 记录恢复耗时、验证方法和负责人；
- 确认 `backend/uploads/` 或 OSS 资源有独立备份策略。

验收：可以从指定 `.bak` 启动后端，健康检查通过，新闻、页面、团队和媒体引用可读取。

#### P0-3 数据库迁移纪律

要求：

- 每次表结构变化只新增顺序迁移，不直接改生产数据库；
- 迁移必须可重复运行，失败时完整回滚；
- 增加从空数据库和旧数据库升级的测试；
- 迁移前自动在线备份，禁止直接复制运行中的 SQLite 主文件。

验收：`npm test` 在空库、旧库和重复迁移场景全部通过。

#### P0-4 错误日志与运行状态

要求：

- 为未捕获异常、API 5xx、迁移失败和上传失败提供结构化日志；
- 日志不得包含密码、JWT、Cookie、OSS 密钥或完整个人资料；
- 增加轻量运行指标：请求错误数、接口耗时、数据库备份结果、PM2 重启次数；
- 为部署失败和健康检查失败设置通知。

验收：开发者能通过一次请求 ID 找到对应错误；生产异常可以在不查看用户敏感数据的情况下定位。

### P1：让后台真正好用

#### P1-1 统一操作反馈

要求：

- 保存、发布、删除、上传、排序等操作统一显示处理中、成功和失败状态；
- 按钮提交期间防止重复操作；
- 错误信息说明“发生了什么”和“下一步怎么做”；
- 离开未保存页面前提醒用户；
- 成功后只刷新受影响区域，避免整页闪烁。

验收：普通管理员不查看浏览器控制台，也能理解操作是否完成以及如何恢复。

#### P1-2 简化页面与新闻编辑流程

要求：

- 首次进入编辑器时突出标题、摘要、封面、分类和发布状态；
- 高级 SEO、历史版本和组件设置默认折叠；
- 中英文缺失只在准备发布或存在未完成草稿时提示；
- 发布前检查结果可点击并自动定位到问题字段或区块；
- 草稿冲突时提供重新载入和保留内容的安全说明，不允许静默覆盖。

验收：新管理员能在没有培训的情况下完成“新建新闻 → 预览 → 修复问题 → 发布”。

#### P1-3 优化后台信息架构

要求：

- 仪表盘只显示真实待办、最近发布和快捷操作，不重复左侧导航；
- 导航名称、页面标题和按钮动词保持一致；
- 团队身份、成员和前台展示关系在一个工作流中可理解；
- 长列表提供搜索、筛选、排序和清晰空状态；
- 危险操作和普通操作在视觉和位置上明显区分。

验收：用户最多三次点击可以到达目标内容；列表筛选后可以恢复默认状态；刷新页面不会丢失关键筛选或编辑目标。

#### P1-4 响应式和无障碍

要求：

- 重点支持桌面 1440/1280、平板 1024/768 和手机 390 宽度；
- 不出现横向溢出、被遮挡按钮和无法滚动的弹窗；
- 所有操作可通过键盘完成；
- 焦点清晰，表单具有关联标签，错误能被辅助技术读取；
- 遵守 `prefers-reduced-motion`，动画不阻碍操作。

验收：完成一次键盘操作巡检和四种尺寸截图检查，控制台无新增错误。

#### P1-5 统一视觉规范

要求：

- 复用现有颜色、间距、圆角、字体层级和按钮样式；
- 减少嵌套卡片、无意义装饰和过度动画；
- 页面以任务为中心：主操作突出，次要设置后置；
- 新样式尽量使用局部类名，不覆盖全站通用选择器；
- 新组件应有加载、空、错误、禁用和窄屏状态。

验收：同类按钮、表单、弹窗、列表在不同后台页面具有一致行为和视觉语言。

### P2：降低长期维护成本

#### P2-1 拆分大型页面组件

优先检查新闻编辑器、页面工作室和大型渲染组件。将数据请求、状态模型、表单区块和展示组件分开，但不要为了“文件短”而制造无意义抽象。

验收：核心逻辑可以脱离 UI 单独测试；修改一个表单不需要理解整个页面文件。

#### P2-2 补充端到端关键流程

至少覆盖：登录、创建草稿、预览、发布、媒体上传、团队身份调整、数据库迁移和部署健康检查。

验收：关键流程在合并前自动运行；失败时能清楚指出具体步骤。

#### P2-3 性能与资源治理

要求：

- 检查首页 WebGL、粒子、图片和轮播的加载成本；
- 后台列表避免重复请求和无上限数据加载；
- 图片上传时检查尺寸、格式和替代文字；
- 公共页面优先保证内容和操作可用，再加载增强效果。

验收：移动网络下首屏可操作时间明显改善，关闭动画后页面功能仍完整。

## 8. 推荐实施顺序

建议按以下节奏推进，每个阶段都可以独立上线：

1. 第一阶段：权限盘点、备份恢复、迁移纪律、日志告警。
2. 第二阶段：统一操作反馈、错误信息和未保存提醒。
3. 第三阶段：新闻与页面编辑流程、发布检查定位。
4. 第四阶段：导航、团队管理、列表筛选和移动端体验。
5. 第五阶段：组件拆分、端到端测试和性能优化。

每周最多同时推进一个后端任务和一个界面任务。涉及数据库、权限或部署的任务不要与大规模界面重构放在同一个 PR 中。

## 9. 可直接交给 AI 的任务模板

### 9.1 通用维护提示词

```text
你正在维护 HKBA 网站与 CMS。请先阅读 README.md、docs/MAINTENANCE_HANDOFF.zh.md、相关现有测试和目标代码，不要立即修改。

任务：<描述一个明确问题>
用户场景：<谁在什么情况下遇到什么困难>
成功标准：<可观察、可测试的结果>

要求：
1. 先说明影响范围、风险和最小实现方案，等待确认后再改代码。
2. 保留工作区内不属于本任务的改动。
3. 先写失败测试，再实现。
4. 不修改或输出任何密钥、生产数据库、Cookie 或个人资料。
5. 完成后运行相关测试、完整测试和前端生产构建。
6. 汇报修改文件、测试结果、手工验证方法和剩余风险。
7. 未经明确授权，不合并 main、不部署生产、不删除数据。
```

### 9.2 后端任务提示词

```text
请处理维护手册中的任务 <编号>。先追踪对应路由、权限中间件、数据库表、迁移和前端调用者，列出兼容性影响。接口错误必须使用稳定错误码，数据库修改必须新增迁移并覆盖空库、旧库、重复执行和失败回滚测试。不要破坏公开 API 和已有生产数据。
```

### 9.3 界面优化提示词

```text
请优化后台的 <具体页面或流程>，目标是减少管理员完成 <具体任务> 的步骤和困惑。先审计现有信息层级、主操作、反馈、空状态、错误状态、键盘操作和 390/768/1024/1440 宽度表现，再提出方案。沿用现有后台设计语言，不使用无意义卡片、装饰动画或重复导航。实现后提供界面截图检查项和交互回归测试。
```

### 9.4 代码审查提示词

```text
请审查当前分支相对 main 的差异。重点查找数据丢失、权限绕过、迁移不可回滚、并发覆盖、接口兼容、敏感信息泄漏、移动端溢出和无障碍退化。只报告可证明的问题，按严重度排序并给出文件和行号。不要直接修改代码，除非我随后明确要求。
```

## 10. 提交前必须完成的验证

在仓库根目录执行：

```bash
cd backend
npm test

cd ../frontend
node --test
npm run build

cd ..
bash .github/scripts/test-resolve-deploy-bundle.sh
git diff --check
git status --short
```

截至 2026-09-07 的参考基线：后端 211 项测试、前端 95 项测试。测试数量会增长，不能因为数量变化而跳过失败项。

还需要人工检查：

- 登录和登出；
- 仪表盘待办和快捷入口；
- 创建并保存一篇新闻草稿；
- 预览和发布检查；
- 上传一张图片并查看引用；
- 团队身份排序和成员展示；
- 手机和桌面布局；
- 浏览器控制台没有新增错误。

## 11. 如何提交和上传代码

### 11.1 检查修改

```bash
git status --short
git diff
git diff --check
```

确认没有以下文件：

- `.env`、私钥、密钥文本；
- `node_modules/`、`.next/`；
- 生产 `.db`、`.db-wal`、`.db-shm`；
- 用户上传文件和备份文件；
- 与当前任务无关的大量格式化改动。

### 11.2 提交并推送功能分支

```bash
git add <明确的文件路径>
git commit -m "feat: 简短说明"
git push -u origin HEAD
```

如果项目使用的远程名称不是 `origin`，先检查：

```bash
git remote -v
```

当前主维护仓库为 `1622359590/hkba`。远程名称可以不同，但 Pull Request 必须提交到这个仓库的 `main`。

### 11.3 创建 Pull Request

```bash
gh pr create --draft --base main --fill
```

PR 描述至少包含：

- 用户问题和修改目标；
- 主要改动；
- 数据库或接口影响；
- 测试结果；
- 手工验证步骤；
- 部署或回滚注意事项。

审查完成后再将 PR 标记为 Ready，并由项目负责人合并。

## 12. 部署流程

正常上线方式：Pull Request 合并到 `main` 后，GitHub Actions 自动运行 `Deploy to Baota Server`。

部署会执行：

1. 校验部署配置；
2. 连接服务器；
3. 备份现有 SQLite 数据库；
4. 同步代码但保留数据库、备份和上传目录；
5. 安装依赖并执行迁移；
6. 构建 Next.js；
7. 重启 `hkba-api` 和 `hkba-web`；
8. 检查前端、后端和代理健康状态；
9. 保存 PM2 状态。

手动部署只用于明确的发布或恢复操作：

```bash
gh workflow run deploy-baota.yml \
  --repo 1622359590/hkba \
  --ref main \
  -f purge_proxy_cache=false
```

不要为了预览普通功能分支而随意运行生产部署工作流。需要预览时优先在本地或独立预览环境验证。

查看部署状态：

```bash
gh run list --repo 1622359590/hkba --workflow deploy-baota.yml --limit 5
gh run watch <运行编号> --repo 1622359590/hkba --exit-status
```

完整部署配置和数据库恢复命令见 `docs/BAOTA_AUTO_DEPLOY.md`。

## 13. 故障与回滚原则

- 部署失败时不要反复点击重跑，先定位失败阶段。
- 前端构建失败：修复分支并重新走 PR，不在服务器直接改代码。
- 数据库迁移失败：停止写入、保留失败数据库副本，从部署前备份恢复。
- 内容误发布：优先使用 CMS 撤回或历史回退，不直接改数据库。
- 媒体误删：先检查引用和 OSS/上传备份，不用空文件覆盖。
- 密钥疑似泄漏：立即轮换，不仅仅是从 Git 历史中删除。
- 回滚后必须再次检查前端、`/api/health`、后台登录和核心内容。

## 14. 每项任务的完成标准

只有同时满足以下条件才算完成：

- 用户场景和验收标准已经达到；
- 新行为有自动测试，原有测试全部通过；
- 前端生产构建通过；
- 数据库和接口保持向后兼容，或迁移方案已验证；
- 桌面和手机关键流程已人工检查；
- 没有提交密钥、数据库、上传文件和无关改动；
- PR 写清风险、验证和回滚方法；
- 部署工作流及冒烟检查成功；
- 相关维护文档已经同步更新。

## 15. 接手者第一周建议

第一周不要大改架构，按以下顺序熟悉系统：

1. 在本地完整启动前后端并通过健康检查。
2. 阅读 `README.md`、本手册、`docs/admin-manual.zh.md` 和 `docs/BAOTA_AUTO_DEPLOY.md`。
3. 跑完所有测试和前端生产构建，记录当前基线。
4. 用测试数据走一遍新闻、页面、媒体、团队和发布流程。
5. 阅读最近的 Pull Request 和数据库迁移。
6. 从 P1-1“统一操作反馈”中选择一个小页面完成首个 PR。
7. 首个 PR 通过后，再开始 P0 权限或迁移类任务。

如果文档与实际代码冲突，以测试和当前代码为准，但必须在同一个 PR 中修正文档，避免错误继续传递。
